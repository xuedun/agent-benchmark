# Guest 耗时增加的模型验证（书籍 skill 判读）

问题：当前采集的数据能否解释 guest 耗时增加？模型预测与实测是否对得上？

依据：《Systems Performance》§2（性能方程/偏差分析）、§5.4.2（off-CPU 分析）、§6.3.7（IPC/CPI）、§6 MMU/TLB。

---

## 一、书籍判定框架

书 §2 教导的性能分析闭环：
```
提出假设 → 构建模型 → 用实测验证 → 计算残差 → 残差显著则追加调查
```

书 §5.4.2 的 on-CPU/off-CPU 框架映射到本实验：
- **guest（on-CPU）** = vCPU 正在执行代码的时间——受 CPI 影响
- **steal（off-CPU: 调度器抢占）** = vCPU 想跑但没分到核——受 CCL 排队影响
- **idle（off-CPU: IO/同步）** = vCPU 主动等待——本实验中极小

**本分析的对象是 guest（on-CPU 部分）的 CPI 增长。**

---

## 二、模型构建与逐 action 验证

### 2.1 模型

```
CPI ≈ CPI_base + MPKI × DRAM时延 / 1000

访存停顿增长比 = (MPKI_8x × DRAM_8x) / (MPKI_1x × DRAM_1x) = MPKI比 × DRAM比
```

### 2.2 逐 action 核算（用绝对值代入）

#### googleapis-59（覆盖率 98.8%——模型成立）

| 量 | 1× | 8× | 比值 |
|---|---|---|---|
| guest (vCPU·s) | 25.5 | 65.9 | **2.58×** |
| MPKI | 7.88 | 13.34 | 1.69× |
| ch128 (ns) | 134.7 | 203.1 | 1.51× |
| 访存停顿/inst (周期) | 7.88×134.7/1000 = **1.06** | 13.34×203.1/1000 = **2.71** | 2.55× |
| **模型预测 guest 比** | — | — | **2.55×** |
| **实测 guest 比** | — | — | **2.58×** |
| **残差** | — | — | **1.2%（可忽略）** |

**判读**：访存模型 2.55× ≈ 实测 2.58×。mvn 构建是纯访存密集型负载，CPI 增长完全由 MPKI 增长（1.69×）和 DRAM 时延通胀（1.51×）的乘积解释。残差 1.2% 在测量噪声范围内。**✓ 模型成立，数据充分。**

#### opossum-42（覆盖率 92%——模型基本成立）

| 量 | 1× | 8× | 比值 |
|---|---|---|---|
| guest (vCPU·s) | 9.2 | 19.6 | **2.13×** |
| MPKI | 7.22 | 12.17 | 1.69× |
| ch128 (ns) | 133.5 | 183.2 | 1.37× |
| 访存停顿/inst (周期) | 7.22×133.5/1000 = **0.96** | 12.17×183.2/1000 = **2.23** | 2.31× |
| **模型预测** | — | — | **2.31×** |
| **实测** | — | — | **2.13×** |
| **残差** | — | — | **-7.8%（模型略超）** |

**判读**：模型 2.31× 略超实测 2.13×（超出 7.8%）。原因：CPI_base（非访存部分）在 8× 下被摊薄——线性外推假设 CPI_base 恒定，但实际占比下降。**✓ 模型基本成立。**

#### plexsystems-58（覆盖率 75%——部分成立，有残差需追加调查）

| 量 | 1× | 8× | 比值 |
|---|---|---|---|
| guest (vCPU·s) | 2.0 | 8.6 | **4.30×** |
| MPKI | 6.60 | 13.44 | 2.04× |
| ch128 (ns) | 133.7 | 210.6 | 1.58× |
| 访存停顿/inst (周期) | 6.60×133.7/1000 = **0.88** | 13.44×210.6/1000 = **2.83** | 3.21× |
| **模型预测** | — | — | **3.21×** |
| **实测** | — | — | **4.30×** |
| **残差** | — | — | **25%未解释** |

**残差追加分析**（书 §5.4.2 off-CPU 方法——此处是"on-CPU 内的额外停顿"）：

| 残差候选 | 量化（用 v3 采集数据） | 占 guest 增量 |
|---|---|---|
| **i-cache 回填** | 1×: 27M×100ns/16VM=0.17s→8.3%；8×: 1705M×100ns/128VM=1.33s→15.5% | **+7.2pp** |
| **TLB 页走** | 1×: 1.5M×3×130ns/16VM=0.04s→1.8%；8×: 86M×3×150ns/128VM=0.30s→3.5% | **+1.7pp** |
| 合计已识别 | — | **~9pp** |
| 仍未解释 | — | **~16%** |

**判读**：访存模型解释 75%，TLB/i-cache 追加解释 ~9%，仍有 ~16% 未解释。可能来自指令数增长或 SMT。**△ 模型部分成立，需要更深工具。**

#### nats-71（不适用——steal 掩盖）

| 量 | 1× | 8× |
|---|---|---|
| guest (vCPU·s) | 19.9 | 24.5（仅 **1.23×**） |
| steal (vCPU·s) | 0 | 29.3 |
| steal 占 wall 增量 | 0% | **82%** |

**判读**：模型预测访存停顿增长 2.85×，但实测 guest 仅 1.23×。**这不是模型错误**——nats 的 vCPU 在 8× 下被偷走 82% 的时间（steal），根本没机会跑够久来"体验"访存变慢。guest 只积累了 1.23× 的时间因为它只跑了很短的时间。

**书 §5.4.2 的对应**：这就像 off-CPU 分析中的情况——线程大部分时间不在 CPU 上（被抢占），on-CPU 时间自然短。性能瓶颈不在"跑得慢"而在"没机会跑"。**→ 此 action 的瓶颈是 steal（CPU 排队），不是 guest（访存变慢）。**

## 三、总结判定

### 3.1 "能否解释清楚"的回答

| Action | 模型覆盖率 | 判定 | 书籍标准 |
|---|---|---|---|
| googleapis | **98.8%** | ✓ 完全解释 | 超过 90/10 规则 |
| opossum | **92%** | ✓ 基本解释 | 达到 90/10 规则 |
| plexsystems | **75% + 9% = 84%** | △ 大部分解释 | 接近但未达 90%，有 16% 残差 |
| nats | **N/A** | → 不适用（steal 主导） | 应换用 off-CPU（steal）视角 |

### 3.2 "数据能否对应实际耗时"的回答

**能，但有口径边界需要明确**：

| 数据 | 能对应什么 | 不能对应什么 | 原因 |
|---|---|---|---|
| MPKI（CCL 聚合） | ✓ 该 CCL 整体的 miss 率变化趋势 | 单个 VM 的精确 miss 率 | 128 个 VM 的聚合，无法分离 |
| ch128（VM 内探针） | ✓ 该 VM 实际感受到的 DRAM 时延 | — | 直接在受害 VM 内测量 ✓ |
| ch8（VM 内探针） | ✓ L3 驻留状态的定性指标 | 精确的命中率 | 混合值（命中+miss 的加权平均） |
| 带宽（DDRC 实测） | ✓ 系统级内存流量与利用率 | 单个 VM 的流量份额 | 硬件级计数，无法按 VM 分 |
| inst/IPC（CCL 聚合） | ✓ CCL 整体执行效率 | 单 VM 的指令数恒定性 | 同 MPKI |

**核心限制**：CCL 聚合口径使精确的 per-VM 闭环核算不可行——但**比值（8×/1×）是可靠的**，因为两轮的聚合口径一致。比值驱动的模型验证（如上）是本分析的方法论基础。

### 3.3 书籍视角的最终评语

> 书 §2："性能分析是迭代的——先建立最简单的模型，用测量验证，如果残差显著则逐步深入。"

本分析的迭代路径：
```
第一轮：分解发现 steal+guest → 定位两个成分
第二轮：访存模型（MPKI×DRAM）解释 guest → 覆盖率 75-99%
第三轮：TLB/i-cache 追加解释 → 覆盖率提升至 84%（plexsystems）
```

**googleapis 和 opossum 的 guest 增加已经被清楚解释**（访存层级争抢，覆盖率 92-99%）。**plexsystems 还有 16% 残差**需要更深工具（如 SPE 或 off-CPU 剖析）。**nats 的问题不在 guest 而在 steal**——应从 CPU 排队视角分析而非访存视角。

## 四、如果要进一步提升覆盖率

| 手段 | 预期收益 | 成本 | 优先级 |
|---|---|---|---|
| SPE（arm_spe_0 数据源标注） | 直接给出每次访存的层级+时延 | 需验证 guest 模式穿透 | 高（若可用） |
| per-VM 指令数（eBPF/perf 于 vCPU 线程） | 排除指令数变化残差 | KVM guest 模式限制 | 低（已知 1-10% 捕获） |
| SMT sibling 并发分析 | 量化 sibling 争用 | percpu.csv 已有数据可分析 | 中 |
| 指令级剖析（perf record -g） | 精确的代码路径 CPI 分解 | 采样开销大 + guest 模式限制 | 低 |
