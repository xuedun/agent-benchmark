# 8× 超分重放劣化分析总纲

负载：AgentENV 轨迹重放（2 vCPU/4GB per VM），1×=384 VM vs 8×=3072 VM，原场景带 delay。
重点对象：四个 4×+ 劣化 build action（opossum-42 / googleapis-59 / nats-71 / plexsystems-58）。
本目录文档按"三步走"组织，每步的原始数据、方法、结论分开沉淀。

## 第一步：耗时分解（已完成）

**文档**：`分解分析第一阶段.md`（主）+ `慢化最多action_8x.md`（action 级定位）

**核心发现**：8× 下四 action 的 Δwall 分解为（1×/8× 全拷贝，账目闭合误差 <1.5s）：

| Action | Δwall | guest（内存stall） | STEAL（vCPU排队） | sys | idle |
|---|---|---|---|---|---|
| googleapis-59 | +66.8s | +20.2 (30%) | **+44.9 (67%)** | +0.4 | +1.3 |
| nats-71 | +17.8s | +2.3 (13%) | **+14.7 (82%)** | +0.2 | +0.7 |
| opossum-42 | +14.0s | +5.2 (37%) | +4.9 (35%) | +0.2 | +3.6 |
| plexsystems-58 | +8.8s | +3.3 (37%) | **+5.3 (60%)** | +0.1 | +0.1 |

结论：劣化 = **steal（35-82%，齐射期 CPU 排队）+ guest（13-37%，访存变慢）**；sys 1-3% 可忽略。

## 第二步：访存分析（进行中，数据待回填）

**文档**：本文件（框架已建，数据段留白待 8× v3 轮完成后填写）

**目标**：把 guest 成分（×1.2-4.3 的执行变慢）定量归因到访存层级，回答"访存对 guest 的影响有多少"。

**分解模型**：

```
guest 时间 ≈ 指令数 × [ 基础CPI + 访存停顿 ] / 频率

访存停顿 = (LPI − MPKI) × L3时延/1000 + MPKI × DRAM时延/1000
           └── 命中部分（时延≈常数~20ns）──┘ └── miss部分（时延=排队敏感）──┘

ΔT_访存(8×−1×) ≈ inst × [ ΔMPKI × (DRAM−L3) + MPKI_8x × ΔDRAM ] / 1000
                   └── 容量项（命中变miss）──┘ └── 延迟项（miss变贵）──┘
```

**采集参数**（v3 管线，1× 正式轮已完成，8× 待重发）：

| 参数 | 方法 | 1× 基线 | 8× | 状态 |
|---|---|---|---|---|
| L3 MPKI / miss 率 | per-CPU 系统 perf（含 guest 执行） | 5.1-9.0 / 61-78% | 待采 | 1× ✓ |
| L3 时延（命中平台） | cpu 计时探针 ch8（1×-before 标定，≈常数） | 17-20ns | 同标定 | ✓ |
| DRAM 时延（miss 代价） | cpu 计时探针 ch128 | 135ns | 待采 | 1× ✓ |
| 指令数（恒定性检验） | per-CPU perf | 3.0-14.8G | 待采 | 1× ✓ |
| **内存带宽（利用率 ρ）** | hisi_ddrc flux_rd/wr（48 控制器，uncore 不受 KVM 切换，guest 全额） | 待采 | 待采 | **待补** |
| 交叉验证 | ch8 实测 ≈ 命中率×L3 + (1−命中率)×DRAM | 待 8× | | |

**已完成的方法学验证**（详见 `实验一/二/三` 文档）：
- KVM 下宿主 per-FC perf 捕获 guest 仅 1-10% → 改用系统级 per-CPU（捕获率 ≥100% 已实证）
- MONOTONIC 探针混入 steal → 改 CLOCK_THREAD_CPUTIME_ID
- E2 受控加压已证两种指纹：容量臂（A22 → miss 率增）与延迟臂（B512 → DRAM 时延增）可分离
- 缺页不是负载敏感因素（minflt 率 1×→8× 反降）

## 第三步：steal 成因分析（已完成）

**文档**：`实验三_steal成因.md`

**核心发现**：Pearson(同 CCL vCPU wait, steal) = **0.935**（n=384），分位严格单调（wait 2→41 核，steal 6%→66%）——steal 直接由该 vCPU 所在 CCL 的排队强度决定。

**成因链**（每环有实测）：轨迹 delay 相位锁定 → 重型构建同窗齐射（~900 可运行 vCPU/384 核）→ CCL 需求超订 → vCPU 排队（wait）→ guest 视角 steal。

**软件零成本优化暗示**：打散相位（错峰调度/并发构建准入）可直接消掉 steal——与加核/改内存形成互补药方。
