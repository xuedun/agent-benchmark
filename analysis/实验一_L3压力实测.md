## 二、本轮发现的两个测量有效性问题（本身是重要产出）

1. **宿主侧 per-FC perf 不进入 guest 模式**：对账实测——单 VM perf cycles 合计 12.58 核·秒 vs 同期 FC utime 119.8 vCPU·s，**捕获率仅 10.5%**。ARM KVM 在 vCPU 进入 guest 时切换 PMU 上下文，宿主 per-thread 事件不计 guest 执行。⇒ A1 的 per-action IPC/MPKI 一列只反映 KVM exit 路径（宿主态），**不能作为 guest 代码的 MPKI 证据**（本轮闭环核算因此作废，不用）。系统级 `perf -a` 不受此限（此前 L3 污染实验与 host-wide 数据有效）。
2. **MONOTONIC 计时的 VM 内并发探针混入 steal**：延迟守护与构建并发跑在同一 VM，齐射期 vCPU 被偷 50% 时，探针墙钟被拉长——8× 的 ch8 699ns / ch128 879ns 是"内存时延 + 被偷时间"的混合值。⇒ 已改用 `CLOCK_THREAD_CPUTIME_ID` 计时（纯在核时间，chase v2），E2 起生效；A1 的时延值只作方向性参考（1× 时 VM 闲置、steal=0，1× 基线 22-28ns 是干净的）。

## 三、阶段性结论（仅基于有效数据）

1. **8× 下 VM 内访存环境显著恶化——方向确定**：即便混入 steal，ch8/ch128 的 before 值（VM 闲置、无自逐出）也从 1× 的 22-28/134-171ns 升至 8× 的 183-427/243-499ns（纯时延部分被 steal 虚增，但 1×→8× 的膨胀方向与宿主侧独立测量一致：8M 探针 27→111-131ns、256M 114→146-178ns）。
2. **缺页不是负载敏感成分**：minflt 率 1×（2.8-20k/s）→ 8× 反而下降（fault 总量近似恒定、wall 拉长所致）⇒ 缺页开销是 action 内禀属性（mvn JVM 类加载 12k/s 最重），不随超分恶化。
3. **episode 合并后的 wall 比更陡**（×4.4-7.7，比第一阶段的片段均值比 ×2.6-5.6 更高）——第一阶段片段均值低估了整步劣化（片段把长波浪切碎平均）。
4. **定量归因的路径修正**：guest 成分的 MPKI×时延闭环在本平台不可用宿主 per-FC perf 完成——改由 **E2 受控加压实验**（污染器梯度 + cpu 计时探针 + guest 时间直接测量）承担定量，E1 保留时延方向性证据 + 缺页排除 + 测量学发现。
