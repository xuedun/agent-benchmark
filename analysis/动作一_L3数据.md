# 动作一：四重点 action 的 L3/内存数据（第一阶段后续）

目标：把分解分析中的 guest 成分（内存 stall）定量钉到 **L3 容量 vs DRAM 延迟 vs 缺页**，per-action 闭环。

## 一、采集扩展（在第一阶段三件套之上新增）

| 组件 | 内容 | 验证状态 |
|---|---|---|
| perf -p FC（每目标 VM 一实例） | `-e cycles,instructions,LLC-loads,LLC-load-misses -I 1000`，窗口积分 → **IPC / MPKI / miss 率** | ✓ 384×1 无 delay：28 实例出数 |
| VM 内延迟守护（latd.sh） | 每 ~20s 跑 chase8M（L3 尺度）+ chase128M（DRAM 尺度）各 150 万次迭代 → 窗口内/窗口前对比 | ✓ before/during 分离清晰 |
| FC 缺页采样 | /proc/PID/stat 的 minflt/majflt 差分 → 窗口内缺页速率 | ✓ |
| 探针注入兜底 | VM 内 gcc 编译（go/node 镜像）→ 静态二进制 base64 分块上传（无 gcc 镜像） | ✓ 28/28 |

验证轮数据（384×1 无 delay，相位锁定齐射 ≈ 重争抢条件）：齐射期 ch8 108→244ns、ch128 165→295ns（googleapis）；mvn 缺页 4.9k/s；IPC 0.42（go build）~2.68（go test）。

### 2.2 对比与归因

- **wall 比（episode 口径）**：googleapis ×7.7、nats ×5.2、opossum ×4.4、plex ×6.2（比第一阶段片段均值比 ×2.6-5.6 更陡——片段均值把长波浪切碎平均，低估整步劣化）
- **IPC/MPKI 列作废**：宿主 per-FC perf 对 guest 模式捕获率仅 10.5%（对账实测：cycles 合计 12.58 核·秒 vs utime 119.8 vCPU·s），ARM KVM 切换 PMU 上下文所致——本轮重要测量学发现
- **时延值含 steal 混杂**：MONOTONIC 计时的并发探针在齐射期被拉长（8× 的 699ns 非纯时延）；chase 已改 cpu 计时（v2），E2 起生效
- 定量归因改由 E2 受控加压承担（见《实验二_L3加压.md》）：A22 臂 ch8 142-218ns ≈ 真实 8× before 值 183-427ns

## 三、判读框架（数据回来后按此填）

| 指标组合 | 结论 |
|---|---|
| MPKI 8×/1× ↑ + ch8 before 基本持平 | L3 容量损失（失配增多） |
| ch128 ↑ 显著 + MPKI 增幅有限 | DRAM/互联延迟（每次失配更贵） |
| minflt 速率 ↑ + majflt 出现 | 缺页/回收介入（容量侧） |
| IPC 降幅 ≈ wall 增幅 | 计算时间全喂给 stall |
| 与第一阶段 guest Δ 对账：Δguest ≈ 指令数 × ΔMPKI × ch128 / 1000 | 定量闭环验证 |
