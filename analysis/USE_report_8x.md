# 8 超分轨迹重放耗时增加分析报告（USE 方法）

机器：debian188（Kunpeng 950 7592C：384 CPU / 24 CCL / L3 22.75MiB 每 CCL / 1.5TB DDR4 / 2.6GHz / schedutil）
负载：agent-benchmark 轨迹重放（每 VM 2 vCPU / 4GB，模板快照启动），base 384；ratio 8 → 3072 并发 VM（128 VM/CCL，6144 vCPU 线程）；total-multiplier 2 → 总量 6144 VM 按完成补位
对照：1× = 384 并发 VM（16 VM/CCL）
日期：2026-11-16/17。分析：opencode。

---

## 0. 摘要（TL;DR）

**8× 超分下重放执行时间 ×2.62（8_1 vs 1_1 avg）、×4.33（8_2 vs 1_2），根因是共享内存层级的争抢——不是核不够、不是磁盘、不是调度排队：**

| 结论 | 一句话 | 证据强度 |
|---|---|---|
| **主因：CCL 内 L3 容量被并发构建打穿** | 128 VM/CCL 活跃工作集 ~25-100MB vs L3 22.75MB；客户机内 8MB 随机访问 12ns → 30-84ns（**×2.5-6.8**） | ●●●（VM 内探针直接测量） |
| **次因：DRAM/内存系统延迟膨胀** | 客户机内 128MB 随机访问 109 → 157ns（**+44%**）；宿主侧 256M 探针 +38% | ●●● |
| **放大器：构建负载本身随机访问密集** | go/npm/mvn 的编译/解析在数十-上百 MB 工作集上随机访问；连 `find`/`rm` 的元数据遍历也是随机访问 → 全类型均匀 ×2.3-2.8 | ●●●（类别表+探针） |
| **长尾（P95/P99）：内存容量耗尽** | 8×2 下 15.6 分钟打满 1.5TB → kswapd 7 万页/s + direct reclaim → vCPU 排队 wait/run 1.8-4.2 → 长命令再 ×2-3 | ●●●（看门狗实测） |
| **排除项** | CPU 核（稳态 busy 仅 ~50%，vCPU 排队 ≈0，p99 仅 21 核）；磁盘（util 12-24%，await≈0，PSI io 0.2%）；频率（2.6GHz 保持）；单 VM 计算能力（负载下纯计算探针 ×1.08）；控制面（command 提交 2.7→20ms，绝对值小） | ●●● |

**判决性实验（单 VM 在 8× 负载下）**：纯计算 0.86→0.93s（×1.08，几乎不受影响）vs 随机访问 12→30-84ns / 109→157ns——**把瓶颈唯一地钉在内存层级**。

**优化排序：① 每域 L3 容量（或软件侧降每域并发活跃构建）→ ② 降 DRAM 延迟（通道数/DDR5/交错）→ ③ 8×2 场景内存容量翻倍消长尾。加核（不加域）、提频、换盘基本无效。**

### 1.2 USE 方法落地（附录 A 清单 → 本系统资源清单）

对 CPU（核/runqueue）、L3、DRAM/互联、内存容量、磁盘 IO、vCPU 调度、控制面（server/ublk/envd）、频率逐项检查 使用率/饱和度/错误。三个关键测量设计：

- **vCPU schedstat 采样**（/proc/FC/task/fc_vcpu*/schedstat 差分，按 FC 进程 cpuset 归 CCL）："vCPU 想跑而未跑上"的直接排队度量；需线程数稳定区间过滤（VM 创建/退出造成假负 delta）。
- **三源对齐校准**：/proc/stat（须去 guest 双计，否则虚高 15pp）= perf cycles = schedstat run，互证一致后才采信。
- **VM 内判决性探针**：宿主级 perf IPC 会被观测器/池 churn/负载突发污染（见 §6），故机制裁决放在客户机内固定负载探针上。

### 1.3 三源对齐（8× 稳态 10s 窗口实测）

| 源 | 数值 |
|---|---|
| /proc/stat（修正） | busy 198 核 / 384 = 50.3%（朴素全字段法虚报 65.4%） |
| vCPU schedstat | run ≈173 核（客户机执行）；**wait ≈ 0**（无排队） |
| perf cycles | 396G/s ≈ 152-180 核 @2.6GHz（频率实测保持） |

## 2. 问题 1：哪些 action 慢化最多？

### 2.1 类别归因（1_1 → 8_1，拷贝加权；总 ΔT = 194,603s）

| 类别 | 步数 | cmd@1×(s) | cmd@8×(s) | 倍数 | ΔT(s) | 占比 |
|---|---|---|---|---|---|---|
| **go** | 315 | 2.712 | 7.673 | 2.83 | 87,508 | **45.0%** |
| **npm/node** | 238 | 3.905 | 9.640 | 2.47 | 76,444 | **39.3%** |
| **maven** | 42 | 5.295 | 13.649 | 2.58 | 18,982 | 9.8% |
| fs-scan | 2337 | 0.033 | 0.081 | 2.43 | 6,208 | 3.2% |
| shell-其他 | 230 | 0.183 | 0.505 | 2.76 | 4,100 | 2.1% |
| fs-write | 1038 | 0.006 | 0.017 | 2.69 | 624 | 0.3% |
| 其余（git/compile/python/gradle） | 343 | — | — | 1.0-2.5 | 738 | 0.4% |

- **构建/包管理三巨头（go build/test、npm install/build/test、mvn compile）占 ΔT 的 94%**——耗时增量的绝对主力。
- 但**倍数全类别均匀（×2.3-2.8）**，连 `rm -rf`/`find` 都 ×2.4-2.7：这是"每次内存访问变贵"的指纹，不是某类专属瓶颈；单个长构建 ×5-6.6（随机访问随命令长度累积）。
- Top 样本：`go build ./pkg/...` 41→213s、`npm run build` 20→123s、`mvn clean compile` 14→95s。
- 失败命令数随拷贝数线性（546→4368 = 精确 ×8）→ 逐拷贝失败率恒定（镜像 `_JAVA_OPTIONS=preferIPv6Addresses` 等确定性失败），不污染对比。
- 控制面 command_start_sec：2.7ms → 7.2ms(8_1) → 20.4ms(8_2)。
- 早停依据：ΔT 累计覆盖 rel 1200s→80%、1500s→96%。

## 3. 问题 2：USE 分析（8× 瓶颈定位）

### 3.1 判决性实验：单 VM 探针（空载 vs 8× 负载，各 3 轮）

在 8× 稳态负载中（6144 vCPU 线程、~155 核在跑、wait≈0）创建一个探针 sandbox，跑固定负载：

| 探针（VM 内执行） | 空载 | 8× 负载 | 比值 | 判读 |
|---|---|---|---|---|
| 纯计算（awk 2000 万次整数循环，L1 驻留） | 0.86s | 0.93-0.99s | **×1.08** | vCPU 计算能力未受损 |
| **随机访问 8MB（CCL L3 尺度）** | **12.2ns/次** | **30.4, 30.4, 83.5ns** | **×2.5-6.8** | **L3 命中率崩塌** |
| **随机访问 128MB（DRAM 尺度）** | **109ns/次** | **152-161ns** | **×1.44** | 内存系统争抢 |
| tmpfs 顺序带宽（300MB cat/dd） | ~10-14GB/s | ×1.0-1.15 | 流式带宽不受影响 |
| 冷读（guest cache drop 后） | 9-23ms | ×1.2 | IO 路径无恙 |

**结论：唯一显著退化的是随机访问内存延迟。** 构建命令（编译器/解析器/包管理器在数十-上百 MB 工作集上随机访问）的时间 ≈ 访问次数 × 延迟 → 全类型均匀 ×2.3-2.8，与 §2 完全互证。

### 3.2 USE 证据总表（8× 稳态 = 并发 3072 VM）

| 资源 | Utilization | Saturation | Errors |
|---|---|---|---|
| **CPU（384 核）** | **~50%**（busy 198 核；vCPU run 93-213 均值 155；内核/守护 ~25-74 核） | **无**：vCPU wait/run 0.001-0.07（wait p99=21 核）；PSI cpu_some 0.3-3.7%；procs_running<300 | 无 throttling |
| **L3（22.75MB×24）** | 容量型 | **重度**：VM 内 8MB 随机 12→30-84ns；宿主 8M 探针 27→111-131ns；MPKI 4.5→8.6-12.2；LLC miss 率 ~70% | — |
| **DRAM/互联** | ~50GB/s（估算 30-40% 实用带宽） | **中度**：VM 内 128MB 随机 109→157ns；宿主 256M 探针 114→146-178ns | 无 ECC 错 |
| **内存容量** | 8×2：AnonPages 19→1408GB（~1.5GB/s 增长） | **8×2 15.6 分钟耗尽**：kswapd pgscan 70k 页/s、direct reclaim 14.6k/s、pgmajfault 217/s；8×1 峰值 1163GB 未耗尽 | dmesg ndisc 邻居表溢出；看门狗 <15GB 停跑 |
| **磁盘（nvme）** | util 12-24%，~7k IOPS | **无**：await≈0ms、PSI io 0.2% | 无 |
| **频率** | 2.6GHz 保持（schedutil，负载下实测） | 无降频 | — |
| **控制面** | server 2.05 核 / ublk 2.9 核（p95 5.7） | command_start 2.7→20ms；监控采样退化（见 §6） | SIGINT 被吞；ndisc 溢出 |
| **网络** | 沙箱 egress REJECT（构建无网） | — | mvn IPv6 确定性快失败（两格恒定） |

### 3.3 负相控制（为什么不是别的）

1. **不是核不够**：CPU busy 50%；6144 vCPU 线程任意时刻仅 ~155 在跑（其余 halt），runqueue wait p99 仅 21 核。
2. **不是调度排队**：上表 + 单 VM 纯计算 ×1.08。
3. **不是磁盘**：util ≤24%、await 0、guest 冷读 ×1.2。
4. **不是频率**：负载下 scaling_cur_freq = 2.6GHz。
5. **不是单 VM"变慢"**：探针 VM 在满负载下计算/带宽/IO 全正常——**慢的是"很多 VM 同时做随机访问密集型工作"这件事本身**。

### 3.4 三段式动态（profile_8x 全程，`analysis/dose_response.csv`）

| 阶段 | bench 时段 | MPKI | MemFree | vCPU wait/run | 特征 |
|---|---|---|---|---|---|
| ramp | 0-2min | 3.7→7.1 | 1415→1160GB | ~0 | 并发爬坡，延迟开始劣化 |
| **A 稳态** | 2-11min | 8.6-12.2 | 1160→406GB | **0.001-0.07** | 纯内存层级瓶颈（本报告主体） |
| B 压力爬升 | 11-15min | 12→21 | 406→74GB | 1.8→4.2 | 回收风暴点燃排队 |
| C 耗尽 | 15min+ | ~20 | <10GB | 2-4 | direct reclaim 阻塞 page fault；看门狗触发（MemFree 14GB） |
| teardown | +28min | →4.5 | 回收 | — | 全指标回基线（因果闭环） |

B/C 期解释原 8_2 的 P95=547s / P99=724s（vs P50=104s）：在该阶段执行的命令叠加回收阻塞 + 排队，再慢 ×2-3。

## 4. 问题 3a：为什么慢？受限资源与占比

### 4.1 机制链（每一步都有直接测量）

```
128 VM/CCL 的活跃构建 → 每域工作集需求 ~25-100MB ≫ L3 22.75MB
  → L3 命中率崩塌（VM 内 8MB 随机 12→30-84ns）
  → 失配访问落到 DRAM，且 DRAM/互联本身延迟 +44%（109→157ns）
  → 每条指令的平均内存停顿 ×2.4-2.7
  → 命令墙钟 ×2.62（与 per-step 实测一致）
```

### 4.2 一致性核算（vCPU-run = exec）

- 8_1 每 VM exec 102.5s × 3072 VM / 2066s ≈ **152 核** —— schedstat 实测 run 均值 **155 核** ✓
- 内存停顿周期仍占用 vCPU（核在"等"不在"算"）→ 解释 CPU 仅 50% 且 vCPU 无排队、却总耗时 ×2.6 ✓
- 1_1：39.1s × 384 / 1946 ≈ 7.7 核 ✓（1× 突发 p95 33 核——1× 构建突发也开始轻度超 L3，说明退化是连续函数而非阈值）

### 4.3 归因占比（对 ×2.62 的分解，基于 VM 内探针的延迟增量）

| 成分 | 量 | 占比估算 |
|---|---|---|
| **L3 容量（命中率崩塌）**：原本 12ns 的访问变 30-84ns | 若构建 60% 访问本可 L3 命中：+18-72ns × 0.6 ≈ +11-43ns/次 | **~55-65%** |
| **DRAM/互联延迟膨胀**：157-109 = +48ns（乘到全部失配访问） | +48ns × 失配占比 | **~25-35%** |
| 排队/其他（稳态） | wait/run ≤0.07；探针计算 ×1.08 | **~0-5%** |
| （仅 8×2 长尾）容量耗尽→回收+排队 | P95/P99 再 ×2-3 | 长尾专用 |

### 4.4 交叉验证清单

exec ×2.62（匹配步）＝ VM 内随机延迟 ×1.4-2.7 ⊕ MPKI 4.5→8.6-12.2 ⊕ vCPU-run=exec ⊕ wait≈0 ⊕ CPU 50% ⊕ 磁盘闲 ⊕ 频率稳 ⊕ 单 VM 计算不慢 —— **九项独立证据同指向，无反例**。

## 5. 问题 3b：硬件优化建议（按预期收益排序）

| # | 优化 | 预期（8× 稳态） | 机理 | 备注 |
|---|---|---|---|---|
| 1 | **每 CCL L3 22.75→~100MB（4.4×）**；或等效增加 L3 域数 / 软件限每域并发活跃构建 | ×2.62 → **×1.3-1.5** | 消除主因（命中率崩塌，55-65%） | Kunpeng 950 域结构固定；x86 可用 CAT/更多域近似；**软件侧"每 CCL 并发构建信号量"零成本等效** |
| 2 | **降 DRAM 延迟**：8→12+ 通道、DDR5、更强交错 | ×2.62 → ×1.9；与 #1 叠加 → ×1.2-1.3 | 消除次因（+44% 延迟，25-35%） | 带宽未满（30-40%），买的是延迟 |
| 3 | **内存容量 1.5→3TB**（仅 8×2 需要） | P95 547→~350s、P99 724→~450s | 消灭 B/C 阶段（回收风暴→排队链） | 8×1 场景 1.5TB 已够 |
| 4 | 核数 ×2（**前提：以更多 CCL 域形式**） | 每域活跃构建减半 → ~×1.5；与 #2 叠加 ×1.2 | 同 #1 | **单纯加核不加域无效**（L3/域不变）；当前核已 50% 闲置 |
| 5 | 频率 +20% | exec −3-5% | 随机访问停顿不吃频率；仅 ~15% 时间受频率缩放 | 收益最小 |
| 6 | 更快盘 / 网络 | **无收益** | util 12-24%、await 0、PSI io 0.2%；冷读探针 ×1.2 | 已排除 |

**只能选一项：选 L3（或其软件等效）。** 软件（零硬件成本）三招：每域并发限制（=①）、KSM 页去重缓解容量（=③部分）、修镜像 IPv6 让 mvn 回归真实构建。

## 6. 附：方法与运维发现（对复现者重要）

1. **宿主级 perf IPC 不可作主证据**：观测器 PSS 全量扫描（每秒扫 2-5k FC 的 smaps_rollup，自烧 1-2 核且页表遍历低 IPC）、warm pool 补池/排水（boot/unmap 风暴）、1× 负载自身的构建突发（p95 33-54 核，轻度超 L3）都会污染分钟级 IPC。**机制裁决用 VM 内固定负载探针 + 匹配步 exec + schedstat。**
2. **bench 忽略 SIGINT**（multiprocessing spawn 子进程吞中断；SIGTERM 立效）——早停编排必须用 SIGTERM。
3. **孤儿 spotbox_monitor 会幸存并持续烧核**（本次发现两个，各 100% 一核）——跑对比实验前先清。
4. warm pool fill_target 会棘轮到 5000：实验前后池 churn 会污染测量；对齐池状态再跑。
5. /proc/pressure 的内存文件名是 `memory`（非 `mem`）；/proc/stat 按 CCL 聚合须去 guest 双计（朴素虚高 15pp）。
6. schedstat 聚合需稳定线程区间过滤（VM 进出造成假负 delta）。
7. 6k netns 触发 ndisc 邻居表溢出（非致命）：调 `net.ipv4.neigh.default.gc_thresh*`。
8. 8×2 复现时会撞内存墙（~15.6 分钟）——看门狗（MemFree<15GB SIGTERM）是必要保险，本次已验证有效。
